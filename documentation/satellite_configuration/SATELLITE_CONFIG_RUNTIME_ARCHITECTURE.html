Satellite configuration — runtime architecture & caching

This document describes how the Event Site Manager loads satellite domain configuration at runtime: from the PostgreSQL backend (satellite_domain table) through the REST API, through Next.js request caching, with automatic invalidation when admins change data in /admin/satellite-domains, and with a static fallback (config/satellites.json and NEXT_PUBLIC_SATELLITE_DOMAINS) when the API returns no rows or fails.

High-level overview

Purpose

Satellite domains are separate hostnames (e.g. a tenant marketing site) that authenticate users through the primary Next.js app using Clerk. The app must know:

  • Which hostnames are satellites (Clerk allowedRedirectOrigins, satellite mode detection).
  • Optional branding for auth pages (slim strip above the Clerk card, sign-out allowlists).

That information is stored in the backend database and exposed via GET /api/satellite-domains. The Next.js app does not require a redeploy to pick up admin changes: merged config is cached server-side and revalidated after CRUD in the admin UI.

How caching is achieved

Next.js unstable_cache

The module satelliteConfigRuntime.ts wraps the merged loader in unstable_cache from next/cache:

  • Cache key: a fixed string array ['satellite-configs-merged'].
  • Revalidate: 300 seconds (5 minutes) — time-based revalidation.
  • Tag: satellite-domains-runtime — used with revalidateTag() for immediate invalidation after admin updates.

Cache parameters (summary)

  • unstable_cache — deduplicates work per request lifecycle; stores result for revalidate seconds.
  • revalidate: 300 — maximum staleness without an explicit invalidation.
  • tags: ['satellite-domains-runtime'] — enables revalidateTag('satellite-domains-runtime').
Implementation note: Inside the cached function, the app calls the backend with fetchWithJwtRetry (service JWT from src/lib/api/jwt.ts), not the browser. The fetch uses cache: 'no-store' so the HTTP client does not add a second opaque cache layer beyond unstable_cache.

Data flow: database to UI

Step What happens
1 Rows live in PostgreSQL satellite_domain (hostname, branding fields, tenant_id, enabled, etc.).
2 fetchEnabledSatelliteDomainDtos() requests GET /api/satellite-domains?page=0&size=500&enabled.equals=true&sort=displayName,asc (no tenant filter in runtime path — all enabled satellites for the primary app).
3 satelliteDomainDtoToSatelliteConfig() in satelliteDomainMapper.ts maps flat DTO fields to nested SatelliteConfig / SatelliteBranding.
4 If the API returns at least one row, that list is the runtime source. If zero rows or an error, getSatelliteConfigsSync() reads config/satellites.json or NEXT_PUBLIC_SATELLITE_DOMAINS.
5 getMergedSatelliteConfigs() is consumed by src/app/layout.tsx (Clerk allowedRedirectOrigins, satellite host detection) and by GET /api/public/satellite-domains (browser clients).

Public API and clients

GET /api/public/satellite-domains

Returns JSON:

  • domains — bare hostnames (e.g. mosc-temp.com) for sign-out redirect validation and Header satellite detection.
  • origins — Clerk-compatible origins (www and non-www variants per satellite).
  • satellites — full merged SatelliteConfig array for client-side branding lookup.

This route is listed in Clerk middleware public matchers so unauthenticated clients can read it. It uses the same merged, cached server path as the root layout.

Security note: The public endpoint exposes hostnames and non-secret branding metadata intended for sign-in/sign-out flows. Do not put secrets in satellite branding fields.

Cache invalidation (admin)

revalidateTag

After create, update, or delete via ApiServerActions.ts, the server calls revalidateSatelliteConfigCache(), which runs revalidateTag('satellite-domains-runtime'). The next request that needs merged config recomputes it (subject to Next.js data cache behavior).

Even if invalidation were skipped, staleness would be bounded by the 5-minute revalidate window on unstable_cache.

Static fallback

When it applies: Backend returns HTTP error, empty list, or zero enabled satellites. Then loadMergedSatelliteConfigs() uses getSatelliteConfigsSync(): first non-empty of config/satellites.json satellites array, else NEXT_PUBLIC_SATELLITE_DOMAINS (comma-separated URLs).
Production builds: Changes to config/satellites.json require a redeploy (file is bundled). Database-backed changes do not require redeploy once rows exist and the API is reachable.

Tenant organization vs tenant settings vs satellite domain

Entity Typical role
tenant_organization One row per tenant_id: identity, subscription/billing, org-level logo/colors/contact.
tenant_settings Feature flags, homepage sections, integrations, marketing URLs, logo_image_url, homepage_cache_version, etc.
satellite_domain Per hostname Clerk satellite routing and optional auth-page branding; optional tenant_id link. This is what the runtime satellite pipeline reads for host lists and Clerk.

They are complementary: avoid duplicating business meaning in three places unless product requires denormalization for performance; optional tenant_id on satellite_domain can align a host with a tenant for defaults.
