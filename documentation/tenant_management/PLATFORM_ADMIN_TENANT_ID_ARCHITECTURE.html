Platform Admin Tenant ID — Architecture Guide

Project: event-site-manager  |  Version: 1.0  |  Date: June 19, 2026
Related: Tenant ID Naming Convention  |  Auto Tenant ID Generation  |  Satellite Config Architecture  |  Clerk Auth (v7)

The same Next.js application is deployed as the primary domain (www.event-site-manager.com) and as satellite domains (e.g. www.mosc-temp.com). Each deployment must set NEXT_PUBLIC_TENANT_ID in environment variables. This document explains whether the primary admin deployment needs a tenant ID, where it is used, and whether event_site_manager_admin_1 (or an existing ID such as event_site_manager_admin_00001) is an appropriate value.

ID format standard: TENANT_ID_NAMING_CONVENTION.html — new organizations use {prefix}_{sequence} with minimum 1-digit suffix (1, 2, …).

1. Architecture overview

One codebase serves two deployment roles. Clerk treats event-site-manager.com as the primary domain (sign-in, sign-up, session source). Satellite domains redirect users to the primary for authentication, then sync the session back. Both deployments talk to the same backend API.

2. Do you need NEXT_PUBLIC_TENANT_ID on the primary app?

Short answer

Yes. The application still requires NEXT_PUBLIC_TENANT_ID (or AMPLIFY_NEXT_PUBLIC_TENANT_ID in AWS Amplify). The helper getTenantId() in src/lib/env.ts throws if it is not set.

Even when the primary deployment is used mainly for admin and authentication, many code paths read the env tenant ID as the default tenant context for API calls and feature modules.

Tenant Management (/admin/tenant-management/*) is largely tenant-agnostic: it lists and creates organizations across all tenants. The env tenant ID is not used as the filter for those admin lists. Instead, admin server actions use optional tenant scoping (appendTenantIfPresent / effectiveTenantId) and JWT + X-Tenant-ID for backend context.

3. Where the env tenant ID is used

AreaHow NEXT_PUBLIC_TENANT_ID is used
Backend API (fetchWithJwtRetry) Default X-Tenant-ID header when callers do not override it (src/lib/proxyHandler.ts)
User profiles Default tenantId on create/update (sign-in, profile page, webhooks)
Payments / Stripe Webhook and checkout handlers validate metadata against getTenantId()
Public features Events, gallery, hero images, membership — scoped to env tenant when those routes are used on that deployment
Some admin modules Uploads, sales analytics, ticket operations still call getTenantId() directly
Tenant Management (cross-tenant) Not used as list filter; manages all tenant_organization rows

Platform admin flag: Set NEXT_PUBLIC_ALL_TENANTS_ADMIN=true (and AMPLIFY_NEXT_PUBLIC_ALL_TENANTS_ADMIN=true in Amplify) on the primary deployment. This matches the intended “hub” that manages all tenants. Proxy list routes are tenant-agnostic; the env tenant remains the default for API context and any code that calls getTenantId() directly.

5. Using event_site_manager_admin_00001

Verdict

Yes — it is OK to set NEXT_PUBLIC_TENANT_ID=event_site_manager_admin_00001 for the primary deployment, provided you treat it as the platform’s own tenant record in the database, not as a special value that works without backend data.

Required setup checklist

  1. Create the organization in the database via Admin → Tenant Management → Organizations → New Organization. Use prefix event_site_manager_admin so the generated ID is event_site_manager_admin_00001 (or create explicitly if sequence differs). See Auto Tenant ID Generation.
  2. Point environment variables at that ID (local .env.local and Amplify for the primary app).
  3. Platform admin users: Ensure your Clerk user has a user_profile with user_role = 'ADMIN' (or SUPER_ADMIN). Aligning tenant_id with event_site_manager_admin_00001 is recommended for consistency, though layout admin lookup is currently by userId without env tenant filter.
  4. Optional: Create Tenant Settings for that organization if the primary domain homepage needs branding, hero images, or other tenant-scoped defaults.

6. Recommended .env configuration

Primary deployment (event-site-manager.com)
# Platform admin hub — cross-tenant management
NEXT_PUBLIC_ALL_TENANTS_ADMIN=true
AMPLIFY_NEXT_PUBLIC_ALL_TENANTS_ADMIN=true

# Platform "home" tenant — must exist in tenant_organization
NEXT_PUBLIC_TENANT_ID=event_site_manager_admin_00001
AMPLIFY_NEXT_PUBLIC_TENANT_ID=event_site_manager_admin_00001

NEXT_PUBLIC_PRIMARY_DOMAIN=www.event-site-manager.com
NEXT_PUBLIC_APP_URL=https://www.event-site-manager.com
NEXT_PUBLIC_API_BASE_URL=https://your-backend-api.example.com
Satellite deployment (example: mosc-temp.com)
# Customer site — do NOT use the platform admin tenant ID
NEXT_PUBLIC_TENANT_ID=mosc_customer_prefix_00002
AMPLIFY_NEXT_PUBLIC_TENANT_ID=mosc_customer_prefix_00002

NEXT_PUBLIC_CLERK_IS_SATELLITE=true
NEXT_PUBLIC_CLERK_DOMAIN=mosc-temp.com
NEXT_PUBLIC_APP_URL=https://www.mosc-temp.com

7. Caveats and pitfalls

Public homepage on the primary domain

Events, gallery, and hero content load for whatever NEXT_PUBLIC_TENANT_ID is set. If event-site-manager.com is auth + admin only, public data may be empty or irrelevant unless you configure the platform org’s tenant settings and content.

Stripe and payments

If the primary deployment processes payments, NEXT_PUBLIC_PAYMENT_METHOD_DOMAIN_ID and webhook handlers expect payment metadata tenantId to match getTenantId(). Use the platform tenant ID consistently in Stripe metadata for that deployment.

Do not reuse the platform ID on satellites

Each satellite Amplify app must use its customer’s tenant ID. Only the primary platform deployment should use event_site_manager_admin_00001 (or your chosen platform org ID).

Replacing tenant_demo_002

Local or legacy values like tenant_demo_002 are fine for development. For production on the primary app, switching to a clearly named platform tenant such as event_site_manager_admin_00001 improves clarity and matches the auto-generated ID convention.
